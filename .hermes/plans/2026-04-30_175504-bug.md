# Plan: investigate and fix crash after repeated dice rolls

## Goal
Find and fix the crash that happens after starting a game and rolling the dice multiple times. The user suspects either a memory leak or an accidental infinite loop. The fix must stay within the game/UI code path and avoid unrelated logic changes.

## Current context / assumptions
- The issue occurs after entering play mode and rolling several times.
- The project uses Vue 3 + TypeScript + PixiJS.
- Game rendering and turn/dice orchestration live in:
  - `src/composables/flight-ludo-play-scene/boardRenderer.ts`
  - `src/composables/flight-ludo-play-scene/diceController.ts`
  - `src/composables/flight-ludo-play-scene/turnController.ts`
  - `src/composables/flight-ludo-play-scene/moveController.ts`
  - `src/composables/useFlightLudoPlayScene.ts`
- The code already contains multiple `requestAnimationFrame` loops and timer-based state transitions, so a leak or runaway rerender is plausible.
- User preference: fix only the UI/runtime issue; do not change game rules or unrelated logic.

## Proposed approach
Use systematic debugging to isolate whether the crash comes from:
1. repeated scene reconstruction / Pixi object churn,
2. uncanceled timers / RAF loops,
3. a render path that keeps adding objects without removing them,
4. a specific roll/turn transition path that triggers runaway scheduling.

Focus on evidence first, then apply a single root-cause fix.

## Step-by-step plan
1. Reproduce the crash consistently.
   - Start a game, roll repeatedly, and record how many rolls typically trigger the crash.
   - If possible, note whether the crash happens during idle, during animation, or after a turn transition.
2. Trace the roll → render → turn-advance chain.
   - Inspect `diceController.ts` for every place that schedules RAF or timers.
   - Inspect `turnController.ts` for turn-advance / auto-turn scheduling.
   - Inspect `moveController.ts` for move animation RAF/timers.
   - Inspect `boardRenderer.ts` for object creation per render.
3. Check for runaway render accumulation.
   - Confirm whether each `renderScene()` call fully destroys the previous scene tree before redrawing.
   - Verify whether any child containers or graphics remain referenced after repeated renders.
   - Check whether idle dice / turn accent RAF loops keep triggering full-scene rerenders at high frequency.
4. Check for timer/RAF cleanup gaps.
   - Verify `clearRollTimers()`, `clearTurnTimers()`, `clearMoveTimers()`, and `stopDiceIdleAnimation()` are always called on page switches, restarts, and unmount.
   - Look for transitions where a new timer is scheduled before the old one is fully canceled.
5. Check the piece-rendering path for accidental duplication.
   - Ensure repeated rolls do not create duplicate listeners, duplicate graphics, or duplicate containers that are never destroyed.
   - Confirm `options.scene.removeChildren()` destruction is sufficient and not bypassed during special branches.
6. Instrument the suspicious path if needed.
   - Temporarily add lightweight counters/logs for:
     - number of rendered Pixi children
     - active RAF ids
     - active timers
     - render call frequency per second
   - Use this only to identify the root cause, then remove it.
7. Form a single hypothesis and test the smallest fix.
   - If the evidence points to a render loop leak, reduce the frequency or stop the offending loop when idle.
   - If the evidence points to object churn, ensure the previous scene is destroyed or reused correctly.
   - If the evidence points to duplicate scheduling, centralize the scheduling/cancel path.
8. Add a regression test or source assertion if the bug is traceable to a stable code path.
9. Re-run validation after the fix.

## Tests / validation
- `npx eslint src/composables/flight-ludo-play-scene/*.ts src/ui-layout.test.ts`
- `node --test src/ui-layout.test.ts`
- If a repro test can be added for the crash path, run that targeted test as well.
- `npm run build` after the root cause is fixed.

Manual validation:
- Start a new game.
- Roll the dice many times in a row.
- Confirm the app no longer crashes or freezes.
- Confirm the dice still animates and turns still advance normally.
- Confirm memory/CPU do not climb continuously during idle play.

## Risks / tradeoffs
- The crash may be caused by an interaction between multiple RAF loops rather than one isolated bug, so the first evidence pass needs to be careful.
- Over-fixing by removing animations wholesale would solve the symptom but break the desired UI feel.
- If the issue is a true Pixi scene churn problem, the correct fix may require reusing more objects rather than redrawing everything each time.

## Open questions
- Does the crash happen during the dice idle animation, the roll animation, the landing animation, or after the next turn begins?
- Is the failure accompanied by steadily increasing memory use or by a sudden stack/CPU spike?
- Does the crash happen only on mobile-sized layouts or on all screen sizes?
