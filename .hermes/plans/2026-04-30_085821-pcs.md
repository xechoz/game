# Plan: adapt the flight-ludo UI for mobile devices and PCs

## Goal
Make the Vue 3 + TypeScript + PixiJS flight-ludo app feel good on both mobile and desktop without changing the core rules:
- preserve the gameplay-first, minimal UI style
- keep the board readable on small screens
- keep the play controls outside the board
- ensure the layout scales cleanly across common mobile widths and desktop viewports

## Current context / assumptions
- The app root is `src/App.vue`, with screen-specific UI in `src/components/game/*`.
- The prepare screen is already image-first, but its card layout and spacing likely need responsive tuning.
- The play screen uses a full-screen Pixi canvas plus an HTML toolbar; this needs careful sizing so it works on phones and on large desktop monitors.
- `PlayScreen.vue` already contains responsive CSS branches for smaller widths, so the main work is likely refining breakpoints, spacing, and board/canvas sizing rather than redesigning the whole flow.
- The board geometry and rendering logic live in `src/composables/flight-ludo-play-scene/*`; those should only change if the responsive layout requires different board sizing inputs.

## Proposed approach
Treat this as a responsive layout pass with three layers:
1. **App shell / page container** — keep the whole app centered and full-viewport friendly.
2. **Screen layout** — make prepare, play, and result screens adapt to mobile and desktop breakpoints.
3. **Canvas + controls** — keep the Pixi board sized to the available viewport while ensuring the toolbar stays visible and never overlaps the board.

Prefer CSS-first changes. Only adjust game layout math if the board canvas cannot remain readable with viewport-based sizing alone.

## Step-by-step plan
1. Inspect the current responsive rules in:
   - `src/App.vue`
   - `src/components/game/PrepareScreen.vue`
   - `src/components/game/PlayScreen.vue`
   - `src/components/game/ResultScreen.vue`
2. Define the target responsive behavior:
   - mobile portrait: single-column layout, compact controls, board as large as possible without clipping
   - mobile landscape: keep controls accessible, reduce vertical padding, preserve board visibility
   - desktop: centered board with comfortable margins and no excessive scaling
3. Tighten the app shell so viewport height is stable across devices:
   - verify `100dvh` usage
   - avoid layout shifts caused by browser chrome on mobile
   - keep background treatment consistent across pages
4. Refine `PlayScreen.vue` layout:
   - keep the toolbar above the board
   - on narrow screens, reduce toolbar height/padding and board margin
   - ensure the canvas width/height formula leaves room for the toolbar
   - if needed, separate desktop and mobile board-size formulas with clearer breakpoints
5. Refine `PrepareScreen.vue` for both phone and desktop:
   - keep the card grid readable on small screens
   - preserve large tap targets on mobile
   - avoid squeezing the image-first cards into unreadable widths
   - keep the page visually centered on desktop
6. Check `ResultScreen.vue` for any overflow or cramped button layout on small screens.
7. If the board still feels too large or too small at certain sizes, adjust the responsive canvas sizing constants in the play scene layer rather than hardcoding page-specific pixel values.
8. Verify the experience at representative sizes:
   - phone portrait
   - phone landscape
   - tablet
   - desktop
9. Run the relevant checks after implementation.

## Files likely to change
- `src/App.vue`
- `src/components/game/PrepareScreen.vue`
- `src/components/game/PlayScreen.vue`
- `src/components/game/ResultScreen.vue`
- possibly `src/composables/useFlightLudoPlayScene.ts` if viewport-to-canvas sizing needs to be coordinated
- possibly `src/composables/flight-ludo-play-scene/boardRenderer.ts` if the rendered board needs spacing adjustments to match the resized canvas

## Tests / validation
- `npm run build`
- `npm run lint`
- If the board-size behavior changes, run any targeted tests that cover board layout math, such as:
  - `node --test src/composables/flight-ludo-play-scene/boardLayout.test.ts`
  - `node --loader ts-node/esm --test src/game/board-presets.test.ts`

Manual checks:
- Prepare screen does not overflow on narrow mobile widths
- Play screen board remains fully visible and not covered by controls
- Desktop layout stays centered and not overly stretched
- Buttons remain comfortably tappable on phones
- No horizontal scrollbars appear at common viewport sizes

## Risks / tradeoffs
- Over-tuning mobile breakpoints can make the desktop layout feel too compressed.
- If canvas sizing is adjusted too aggressively, the board may become too small for play on phones.
- Some mobile browsers treat viewport height differently; `100dvh` helps, but browser chrome and safe-area behavior may still require small spacing tweaks.
- If the play toolbar is made denser for mobile, the visual hierarchy must still remain clear enough for back/board controls.

## Open questions
- Should the desktop layout prioritize a larger board or more surrounding breathing room?
- On mobile portrait, should the play screen favor maximum board size or maximum control separation?
- Do we want a single responsive design for both prepare and play screens, or slightly different mobile densities for each screen?
